Building a Windows DFIR box

Build a repeatable Windows workstation for analyzing evidence that has already been collected.

What we’re building

  • A Windows analysis machine, not an evidence acquisition machine.
  • Evidence is already collected; memory acquisition is handled separately (Magnet in our workflow).

The box takes collected artifacts (triage collections, event logs, registry hives, disk images, memory images) and produces analysis output: parsed CSVs, timelines, notes. It never touches the client’s systems.

This is an opinionated build. Each choice below has alternatives; these are the ones that have worked.

Choice Why
Windows Windows Server 2025, Desktop Experience Stable Long-Term Servicing Channel release; Microsoft Defender Antivirus is a feature you can remove; no TPM requirement
Hypervisor VMware Workstation Pro Independent non-persistent disks reset on power-off; Shared Folders, one of them read-only, keep case data outside the VM
Install An unattend file The same Windows build every time, with the settings below already applied
Settings UAC off, Defender removed, long paths on, extensions and hidden files shown Analysis tools run without friction on a machine that is thrown away
Tools Chocolatey, plus a few direct downloads One command line installs most of the list, and records versions

Disposable/nonpersistent virtual machine

  • Return the machine to a known state.
  • Keep case data and analysis output separate from what gets reset.

Why disposable. Analysis tools open hostile files. Each case starts from the same known-good image, nothing carries over from the previous client, and “what version of the tool did we use” has one answer.

VMware Workstation Pro

Workstation Pro has been free for commercial, educational and personal use since November 2024 (Broadcom); download it from the Broadcom support portal.

Lives where On reset
Windows, settings, installed tools System disk, independent non-persistent Discarded at power-off
Temporary files, caches, tool state System disk Discarded at power-off
Evidence Host folder, shared read-only Kept; the VM cannot change it
Analysis output, tool logs, notes Host folder, shared read-write Kept

Non-persistent system disk. Build the VM with a normal disk, install and configure everything, shut it down, then in VM Settings → Hard Disk → Advanced set the disk to Independent and Nonpersistent. From then on, changes are discarded when you power off the VM or restore a snapshot, and the disk is in the same state every time it starts (VMware Workstation Pro documentation). A restart inside Windows is not a power-off; shut down, and power the VM off. To update the image, switch the disk back to persistent, update, and switch it back.

Shared Folders. In VM Settings → Options → Shared Folders, add two host folders: Evidence with the Read-only attribute, so the VM can view and copy files but cannot add, change or remove them, and Cases read-write for output. With VMware Tools installed, they appear in Windows at \\vmware-host\Shared Folders\. Host file permissions still apply.

Verify it. Write a test file to Cases, try (and fail) to write one to Evidence, power off, power on, and confirm the Cases file is still there and a file you left on the desktop is gone.

Automating the build

  • Decide on the Windows image and tool list.
  • Make setup repeatable rather than configuring it by hand each time.

Windows Server 2025

Use the Desktop Experience installation option; the analysis tools need a desktop. Microsoft’s Evaluation Center has a 180-day evaluation, which must be activated online within its first 10 days or it shuts down; activate it during the build, while the VM has a network. A licensed image is the alternative. Why Server rather than Windows 11:

  • Stable. Long-Term Servicing Channel: no feature updates rearranging the system between cases.
  • Defender is a feature. On Windows Server, Microsoft Defender Antivirus is installed as a Windows feature, Windows-Defender, so it can be removed cleanly instead of fought with (Microsoft Learn).
  • No TPM requirement. Microsoft lists a TPM as “required only for certain features,” such as BitLocker (hardware requirements), so the VM needs no virtual TPM, and no encryption of the VM that a virtual TPM brings with it in Workstation.

Unattended install

An unattend file (autounattend.xml) answers every question Windows Setup asks and can apply settings and run scripts. Build one with Christoph Schneegans’ unattend generator. Settings to choose for this box:

Generator setting Why
A local administrator account No Microsoft account; one known login
Disable User Account Control (UAC) See UAC below
Enable long paths Deep paths inside collections otherwise fail
Always show file extensions; show all files invoice.pdf.exe and hidden files are visible
Do not update Last Access Time stamp Reading a file on the box does not change its last access time
Disable SmartScreen Tools downloaded during the build are not blocked
Remove bloatware Fewer distractions and background updates
FirstLogon scripts Install Chocolatey and the tools (below)

The generator is written for Windows 10 and 11, and its files work for Windows Server 2025 once you make two choices by hand:

  • Product key. Choose Enter another product key and enter your own key, or the generic key for the edition from Microsoft’s KMS client product keys (Windows Server 2025 Standard: TVRH6-WHNXV-R9WG3-9XRFY-MY832). The generic key picks the edition; it does not activate Windows.
  • Image. Choose Select image with this name or Select image with this index, and pick a Desktop Experience image. To list the images on the ISO, mount it and run Get-WindowsImage -ImagePath D:\sources\install.wim in an elevated PowerShell (D: being the mounted ISO).

Generate the file again when you change the build, rather than editing the XML by hand.

Windows Setup looks for autounattend.xml in the root of removable media. In Workstation, create the VM with I will install the operating system later (so VMware’s Easy Install does not supply its own answers), attach the Windows ISO, and attach a second small ISO, or a floppy image, containing autounattend.xml.

Configuring Windows for analysis

  • Tools that need to run as administrator.
  • UAC: normally I don’t disable security features, but this is a disposable VM and reducing friction matters.
  • Other Windows security settings as decisions specific to this machine, not general recommendations.

These are the settings, and the command for each if you apply it after setup instead of in the unattend file. Run them in an elevated PowerShell.

Setting Command
UAC off Set-ItemProperty -Path HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System -Name EnableLUA -Value 0, then restart
Remove Microsoft Defender Antivirus Uninstall-WindowsFeature -Name Windows-Defender, then restart (check the name with Get-WindowsFeature *defender*)
Long paths Set-ItemProperty -Path HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem -Name LongPathsEnabled -Value 1
Show file extensions Set-ItemProperty -Path HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced -Name HideFileExt -Value 0
Show hidden files Same key: Hidden = 1
Show protected system files Same key: ShowSuperHidden = 1
No last-access updates fsutil behavior set disablelastaccess 1
Server Manager not at every logon Get-ScheduledTask -TaskName ServerManager \| Disable-ScheduledTask

UAC

With EnableLUA = 0, Admin Approval Mode is off and administrators run everything elevated, so tools that need administrator rights simply work. The middle ground is ConsentPromptBehaviorAdmin = 0: UAC stays on and elevates without prompting, but programs still start unelevated unless asked. See Microsoft’s User Account Control settings and configuration.

Network and updates

Analysis rarely needs the internet; installs and tool updates do. Connect the VM during the build, then keep it off the internet during cases: a host-only network, or none. Hostile files cannot reach out, and the tools stay at the versions in the image. Windows Update in the middle of a case changes the system under the analysis; update the clean image on a schedule instead.

Tools for analysis

  • Select the tools and versions.
  • KAPE modules for processing already-collected artifacts.

Chocolatey and Scoop

Chocolatey installs most of the list from one command, which makes the FirstLogon step one line. Its community packages are maintained by volunteers, separately from the tools’ authors: check the package page links to the real project before adding it. Scoop is an alternative that installs per user without administrator rights; it has fewer DFIR tools.

choco install -y 7zip sysinternals pwsh ericzimmermantools volatility3 autopsy

There is no need to pin versions. The non-persistent disk keeps every tool at the version in the image until you deliberately update it, and Scoop keeps earlier versions side by side when it updates an app (scoop cleanup removes them). Record what is installed for the case notes:

choco list | Out-File -FilePath "\\vmware-host\Shared Folders\Cases\2026-0142\Notes\Tools.txt"

Processing an existing artifact set with KAPE modules

KAPE has two halves: targets collect files from a system, and modules run programs against files already collected. For this box only modules apply. Modules are defined in .mkape files; the community set is maintained in KapeFiles, which includes the compound module !EZParser (runs Eric Zimmerman’s parsers over a collection).

# Module source is a collection that already exists; output goes to case storage.
.\kape.exe --msource "\\vmware-host\Shared Folders\Evidence\2026-0142\C" --mdest "\\vmware-host\Shared Folders\Cases\2026-0142\Output\EZParser" --module !EZParser

Check the switches against kape.exe --help and the KAPE documentation for the version you install.

Licensing. KAPE is free for CRT members. Commercial use, such as paid engagements, requires an enterprise license from Kroll: KAPE license agreement.

Using and resetting the box

  • Run tools against existing artifacts.
  • Retain the results and relevant logs.
  • Verify the environment and reset it for the next case.

A per-case checklist:

  1. Power on from the non-persistent image. Confirm \\vmware-host\Shared Folders\Evidence is read-only and Cases is writable.
  2. Create the case folders with New-CaseFolder from the PowerShell page, and put the evidence in the host’s Evidence folder. Hash it on arrival with Get-FileInventory.
  3. Run tools against Evidence, writing to Cases\<case>\Output. Keep each tool’s console log or log file in Output.
  4. Before power-off, confirm the output is on the Cases share: Get-FileInventory -Path <case>\Output | Export-Csv <case>\Notes\OutputInventory.csv -NoTypeInformation.
  5. Power off. Everything on the system disk is discarded; the next case starts clean.
